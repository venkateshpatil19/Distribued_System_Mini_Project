# Real-world demo: launching an express checkout safely

**Scenario.** An online store wants to replace its three-step checkout with a one-page "express checkout". The code ships dark behind the feature flag `new-checkout`, and DeployGuard decides who sees it. Thousands of store servers (here: agents) must switch consistently, and a bad release must be undone in seconds without a redeploy, even if a controller or a server fails mid-release.

## Run it
Double-click `start.bat` (3 controllers, 3 agents and the dashboard), then `demo.bat` (narrated demo, Enter between steps).
Keep http://localhost:3000/dashboard open to show each step live. Use `-NoPause` to run the steps back to back.

## What each step shows, and the result recorded on the reference run

| Step | Story | Distributed-systems concept | Recorded result |
|---|---|---|---|
| 1 | Show the cluster | Independent processes, Bully leader, heartbeats | leader controller-3, 3/3 agents converged |
| 2 | Dark launch to enterprise customers in staging | Global revision ordering, agents pull new revisions from the leader, targeting rules | revision applied by all agents in 0.1 s; `u1 (enterprise) -> on`, `u2 (free) -> off` |
| 3 | Search ranker 10% -> 50% -> 100% | Leader scheduler, guardrails, convergence before promotion | COMPLETED in about 25 s |
| 4 | Broken express checkout (30% payment errors, simulated) | Automatic rollback, fencing-token-protected writes | ROLLED_BACK in 6-8 s: "error rate 22.22% exceeded limit 5.00%"; every agent on the rollback revision immediately |
| 5 | Leader loses its network | Failure detection between controllers, Bully election, epochs, split-brain safety via fencing | new leader in about 3 s; controller-3 takes back leadership after the partition heals |
| 6 | One store server drops off the network | Beacon protocol (suspicion, not proof), recovery, catch-up by pull | SUSPECTED after 3.1 s, RECOVERING after 6.1 s |
| 7 | Audit trail | Lamport clocks on every event, across nodes | events listed with Lamport times and the node that produced them |

Traffic and faults are generated by the agents' simulator and are labelled `simulated` in the event log and the UI.

## Viva talking points
1. **Why can't the old leader corrupt a rollout after it is partitioned?** Every mutation holds a lease and presents a fencing token. Tokens come from one counter in the replicated state, and the fence guard rejects any token older than the last accepted one (`StateStore.checkFence`). On top of that, a leader that cannot reach a majority stops serving, and followers refuse replication from an older epoch.
2. **How do agents stay consistent if messages are lost, delayed or duplicated?** Revisions are global and totally ordered. An agent applies a bundle only if its revision is newer than the one it holds. Heartbeat replies carry the desired revision, so an agent that is behind pulls the bundle over gRPC.
3. **Why vector clocks as well as Lamport clocks?** Lamport times give a total order consistent with causality but cannot show that two events are concurrent; vector clocks can (`/api/events/compare`).
4. **Is a SUSPECTED agent dead?** Not necessarily. A heartbeat timeout cannot distinguish a crash from a slow or partitioned node, so the state is called "suspected" and the agent can still recover.
5. **What does a rollback cost?** One new configuration revision. Every agent sees it in its next heartbeat reply and applies it within about a second; no build or redeploy is needed.

## Limitations
- Replication is asynchronous (once a second or on change). A write accepted by a leader just before it crashes can be lost; a production system would wait for a majority to acknowledge each write (as Raft does).
- The whole state is copied on every replication, which is fine for a demo-sized state but not for large data.
- No authentication: keep the control plane on a private network.
- Traffic is simulated. Real services would report metrics from their own requests.
